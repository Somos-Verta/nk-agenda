Sellflux — o que ela faz e o que ela não faz

Levantado da documentação oficial em 16/07/2026. Detalhes em SELLFLUX-API.md.

A Sellflux tem agenda, mas não tem capacidade. O recurso /api/v1/crm/schedules é um calendário de compromissos — não existe campo de vaga, lotação ou recurso limitado. Ela não sabe que uma bateria tem 10 karts e não recusaria o 11º piloto. Por isso a grade, a capacidade e o encaixe continuam sendo desta agenda, que é a fonte de verdade. A Sellflux entra como CRM e comunicação: lead, histórico e WhatsApp.
O que usamos da API dela
POST/api/v1/lead— acha ou cria o cliente como lead
GET/api/v1/lead/project?search=— busca por nome, e-mail ou telefone (evita lead duplicado)
POST/api/v1/crm/schedules— cria o compromisso da bateria vinculado ao lead
PUT/api/v1/crm/schedules/{id}— reflete alteração da reserva
POST/automation/v1/whatsapp/lead— confirmação por WhatsApp via template
GET/api/v1/crm/team/users— descobre o acting_user_id

Conexão com a Sellflux

Ao criar ou alterar uma reserva aqui, ela é espelhada na Sellflux: acha/cria o lead, cria o compromisso e dispara a confirmação.

A chave da Sellflux não pode ficar nesta página. Ela dá acesso ao CRM inteiro do projeto, e qualquer pessoa que abrir a agenda leria a chave. O navegador também barra a chamada direta por CORS. Por isso o campo abaixo é o proxy: a rota da nossa API que guarda a chave e repassa para a Sellflux espelhando os mesmos paths.
Desligado
acting_user_id é obrigatório nas rotas de CRM quando a autenticação é por chave de API — sem ele, a Sellflux recusa o compromisso.

Como a bateria vira compromisso

O mapeamento que o painel faz. schedule_type só aceita meeting, call, task ou email — não existe tipo de reserva, então bateria vira meeting.

POST {proxy}/api/v1/crm/schedules Content-Type: application/json // o proxy injeta o Authorization: Bearer <chave> { "subject": "Kart · João Silva · 4 pilotos · Goiânia", "description": "Bateria 19:00 na unidade Goiânia\n4 karts · origem: sellflux", "start_date": "2026-07-20T19:00:00-03:00", "end_date": "2026-07-20T19:20:00-03:00", // início + duração da bateria "timezone": "America/Sao_Paulo", "schedule_type": "meeting", "lead_ids": "100025", // separados por vírgula "acting_user_id": 316372 // obrigatório com chave de API }
Antes disso: achar ou criar o lead
// 1) busca casa por nome, e-mail OU telefone — evita lead duplicado GET {proxy}/api/v1/lead/project?page=1&search=5562999998888 // 2) só cria se não achou → 201 { "id": 100025 } POST {proxy}/api/v1/lead { "name": "João Silva", "phone": "5562999998888", "email": "joao@email.com", "tags": ["kart", "agendamento"], "unidade": "Goiânia", // ↓ campos personalizados "bateria": "19:00", "pessoas": 4 }
Atenção aos campos personalizados: unidade, bateria e pessoas só são gravados se já existirem como campo personalizado no projeto Sellflux. Se não existirem, a Sellflux ignora em silêncio — não dá erro, o dado simplesmente não aparece no lead. Crie os três antes de ligar o espelhamento.
Depois: confirmação no WhatsApp
POST {proxy}/automation/v1/whatsapp/lead { "lead_id": 100025, "template_id": 1, "data": { // variáveis do template "nome": "João Silva", "bateria": "19:00", "data": "2026-07-20", "unidade": "Goiânia", "pessoas": "4" } }
Vai para o telefone primário do lead. Se a confirmação falhar, a reserva local continua válida — o painel só marca o erro, sem desfazer nada.

Sellflux → Agenda (o caminho de volta)

Para a Sellflux criar reserva sozinha, ela precisa chamar a nossa API — porque só ela sabe se a bateria tem vaga. É o POST /agendamentos do contrato acima, chamado por uma automação Flux v2.

Na Sellflux, uma automação com domain_type: "schedule" é disparada por agendamento — é o gancho pronto para lembrete de bateria e follow-up de no-show, sem precisarmos agendar nada do nosso lado. Vale montar depois que o backend estiver no ar.
